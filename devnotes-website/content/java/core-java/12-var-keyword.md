## Introduction

The `var` keyword was introduced in **Java 10** to reduce boilerplate code. Many developers misunderstand `var`. One of the biggest misconceptions is:

> "`var` makes Java dynamically typed."

**This is false.** Java is still a statically typed language. The compiler simply **infers the type from the assigned value**.

```java
var name = "John";
```

The compiler internally treats it as:

```java
String name = "John";
```

The type is decided at **compile time**, not runtime.

## What is Type Inference?

Type inference means the compiler automatically determines the variable's type.

```java
var age = 25;            // compiler infers: int age = 25;
var salary = 55000.50;   // compiler infers: double salary = 55000.50;
```

## Why was var Introduced?

Before Java 10:

```java
HashMap<String, List<Employee>> employeeMap =
        new HashMap<>();
```

Very long. Using `var`:

```java
var employeeMap =
        new HashMap<String, List<Employee>>();
```

Cleaner and easier to read.

## Examples

| You write | Compiler sees |
| --- | --- |
| `var x = 10;` | `int x = 10;` |
| `var price = 250.75;` | `double price = 250.75;` |
| `var language = "Java";` | `String language = "Java";` |
| `var active = true;` | `boolean active = true;` |
| `var list = new ArrayList<String>();` | `ArrayList<String> list = new ArrayList<>();` |
| `var employees = new HashMap<Integer, Employee>();` | `HashMap<Integer, Employee> employees = new HashMap<>();` |

## Java is Still Statically Typed

```java
var number = 10;
number = 20;       // Valid
```

```java
var number = 10;
number = "Java";   // Compilation Error
```

**Reason:** the compiler already determined that `number` is an `int`.

## var with Objects

```java
var employee = new Employee();
// compiler: Employee employee = new Employee();
```

## var with Streams

Without `var`:

```java
Stream<String> stream = list.stream();
```

Using `var`:

```java
var stream = list.stream();
```

Cleaner code.

## var with Lambda Expressions

**Java 11** introduced support for `var` in lambda parameters.

```java
(var name) -> name.toUpperCase()
```

More useful when annotations are needed:

```java
(@NotNull var name) -> name.toUpperCase();
```

## Where Can var Be Used?

### Local Variables ✅

```java
var x = 10;
```

### Inside Loops ✅

```java
for (var i = 0; i < 5; i++) {
    System.out.println(i);
}
```

### Enhanced for Loop ✅

```java
for (var employee : employees) {
}
```

### Try-with-Resources ✅

```java
try (var reader =
        new BufferedReader(new FileReader("test.txt"))) {

}
```

## Where var Cannot Be Used?

### Instance Variables ❌

```java
class Employee {
    var id = 10;   // Compilation Error
}
```

### Static Variables ❌

```java
static var count = 0;   // Compilation Error
```

### Method Parameters ❌

```java
public void display(var name) {   // Compilation Error
}
```

### Method Return Type ❌

```java
public var getName() {   // Compilation Error
}
```

### Without Initialization ❌

```java
var number;   // Compilation Error
```

The compiler cannot infer the type.

### Multiple Variables ❌

```java
var a = 10, b = 20;   // Compilation Error
```

Declare them separately.

### Null Assignment ❌

```java
var obj = null;   // Compilation Error
```

The compiler cannot determine the type. **Correct:**

```java
Object obj = null;
```

## var with Generics

Without `var`:

```java
Map<String, List<Employee>> employees =
        new HashMap<>();
```

Using `var`:

```java
var employees =
        new HashMap<String, List<Employee>>();
```

Much easier to read.

## Readability

**Good example** — the type is obvious:

```java
var employees = repository.findAll();
```

**Bad example** — the reader has no idea what type `result` is:

```java
var result = process(data);
```

> [!WARNING]
> Avoid `var` when the type isn't obvious from the right-hand side.

## Performance

> [!QUESTION] Does var improve performance?
> **No.** The compiler converts `var` into the actual type during compilation. The generated bytecode is almost identical, so there is no runtime performance improvement.

## Reflection

```java
var employee = new Employee();
```

Reflection still reports `Employee`, because `var` exists **only at compile time**.

## Real Project Examples

```java
// Spring Boot
var response = restTemplate.getForObject(...);

// Repository
```

## Advantages

- Less boilerplate
- Better readability for obvious types
- Easier refactoring
- Cleaner generic declarations
- Modern coding style

## Disadvantages

- Can reduce readability if the type isn't obvious.
- Beginners may not understand the inferred type.
- Cannot be used everywhere.

## Interview Questions

### Q1. What is var?

A keyword for **local variable type inference**.

### Q2. Which Java version introduced var?

**Java 10.**

### Q3. Is Java dynamically typed because of var?

No. Java remains statically typed.

### Q4. Can var be used for fields?

No. Only local variables.

### Q5. Can var be assigned null?

No. The compiler cannot infer the type.

### Q6. Can we change the type later?

No.

```java
var x = 10;
x = "Java";   // Compilation Error
```

### Q7. Does var affect JVM performance?

No. It is purely a compile-time feature.

### Q8. Can var be used in loops?

Yes — both traditional and enhanced `for` loops.

### Q9. Can var be used in lambda expressions?

Yes, from **Java 11**.

### Q10. When should we use var?

Use it when the type is obvious from the right-hand side and it improves readability.

## Common Mistakes

- Assuming `var` means dynamic typing.
- Using `var` where the inferred type is unclear.
- Declaring `var` without initialization.
- Trying to use `var` for class fields.
- Assigning `null` to a `var` variable.

## Best Practices

- Use `var` only for local variables.
- Use `var` when the inferred type is obvious.
- Avoid `var` if it hurts readability.
- Continue using explicit types in public APIs.
- Prefer clarity over shorter code.
